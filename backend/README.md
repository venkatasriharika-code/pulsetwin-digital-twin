# PulseTwin — Backend

FastAPI backend implementing the API contract the frontend already expects
(`src/api/types.ts` / `src/api/client.ts` in the frontend repo). No database,
no external services, no API keys required to run it.

## Run it

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Then point the frontend at it: in the frontend's `.env`, set
`VITE_API_BASE_URL=http://localhost:8000`.

Interactive API docs (auto-generated by FastAPI) are at
`http://localhost:8000/docs` once it's running — useful for testing each
endpoint by hand before wiring up the frontend.

## Architecture — how a request flows

This follows the layered design from the project brief:

```
question (text)
   │
   ▼
scenario_parser.py      — rule-based NLP: text → structured ParsedScenario
   │
   ▼
optimizer.py
   ├── queueing.py       — Layer 1: fast M/M/c screen of many candidates
   │                       (cheap, no randomness, screens the full decision space)
   └── simulation.py     — Layer 2: discrete-event simulation of the
                            shortlisted candidates only (virtual patients
                            moving through triage → doctor → testing →
                            treatment → beds → discharge)
   │
   ▼
scored candidates + explained recommendation
```

`main.py` wires these into the four HTTP endpoints:

| Endpoint | What it does |
| --- | --- |
| `GET /api/status` | Current live KPIs, computed live from `data.py`'s baseline config through the queueing engine |
| `POST /api/scenario/parse` | Runs `scenario_parser.py` on the question |
| `POST /api/scenario/evaluate` | Runs the full optimizer: fast-screens candidates, simulates the shortlist, scores, and explains |
| `GET /api/ward/state` | Looks up a previously-evaluated scenario/candidate's simulation snapshot for the Ward View |

## What's real vs. what's a placeholder

**Real and functional:**
- The M/M/c queueing math (`queueing.py`) — genuine Erlang-C formula, not
  faked numbers.
- The discrete-event simulation (`simulation.py`) — an actual event-driven
  simulation with a priority queue, doctor/bed assignment, and severity-aware
  patient flow.
- The optimizer's scoring function is a real weighted objective (critical
  wait weighted far above average wait, plus utilization and staffing-cost
  penalties) — the weights are declared in one place (`optimizer.py`,
  `_score`) so you can tune them.

**Deliberately simplified — swap these out as you productionize:**
- `data.py`'s `BASE_CONFIG` is hardcoded synthetic data. Replace with a real
  feed from your hospital's staffing/bed-management system.
- The in-memory `_scenario_store` in `main.py` loses state on restart and
  won't work across multiple backend instances — swap for Redis/Postgres if
  you deploy more than one instance.
- `scenario_parser.py` is regex-based, not an LLM. It's intentionally
  dependency-free so the project runs with zero API keys. To upgrade it:
  call an LLM with a prompt that asks it to extract the exact same
  `ParsedScenario` JSON shape, and keep everything downstream unchanged —
  the optimizer and simulation don't care how the scenario was parsed.
- The simulation runs a single replication per candidate. For real
  statistical confidence, run N replications with different seeds and
  average — `run_simulation`'s `seed` parameter is already exposed for this.

## Files

```
app/
  main.py             FastAPI app + the 4 endpoints
  models.py            Pydantic models (camelCase JSON, matches frontend types.ts)
  data.py              Baseline ward configuration (synthetic)
  queueing.py           Layer 1: M/M/c fast screening
  simulation.py         Layer 2: discrete-event simulation
  scenario_parser.py    Text → structured scenario
  optimizer.py          Ties layers 1+2 together, scores, explains
```
